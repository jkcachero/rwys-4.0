Then sign in as the existing verified owner, open **Settings > Agent access > My API tokens**, confirm your existing password when asked, select the approved **Client**, enter a **Token name**, select minimum **Read permissions**, and click **Create token** in the **Create API token** form. The API does not accept the browser session as its authentication.

Settings has one **Agent access** sidebar entry at `/settings/agent-access`. Its authenticated, verified, password-confirmed GET rechecks current operator permission: an authorized operator is redirected to `/settings/provider-accounts`; everyone else goes to `/settings/agent-tokens`. Both concrete routes remain functional. Both pages share the **Agent access** heading and tabs **Account assignments** (badge **Operator**) and **My API tokens** (badge **Personal**). Only explicitly permitted operators get an assignment link; everyone else sees the locked tab with **Only operators can assign accounts. Ask an operator for help.**, not a clickable 403 dead end.

Personal token creation requires an active Client owned by the signed-in user; a sole active owned Client is auto-selected. With no active owned Client, **No personal client access** replaces the creation form. An operator sees **Manage account assignments** there but cannot mint tokens for John or another owner. No ownership or ability permissions are widened; inactive owned-Client **Revoke** and the secret lifecycle remain unchanged.

- Plaintext appears once under **Your new token**. Store it in the client's secret store, never a URL, screenshot, source file, chat, or command argument.
- New tokens expire 30 days after issuance; server-wide Sanctum expiration can shorten effective validity.
- **Rotate** immediately deletes the old token and returns new plaintext once. It preserves the exact original expiry, not another 30 days.
- **Revoke** deletes the token. Revocation is supported even when the owned Client is inactive; rotation and issuance require an active Client.
- **Restrict to selected accounts** requires at least one authorized mapping. Without restriction, all current and future eligible materialized accounts linked to that Client's owned profiles are in scope; new remote connections require explicit operator **Sync accounts** first.
- Publishing is opt-in via **Allow publishing (write access)** and requires supported mappings, mapping-level permission, and server gates. It is not granted merely by holding a token.
- Instagram scheduling is a separate explicit **Allow scheduled Instagram images (write access)** checkbox granting `zernio.posts.schedule`, never a read default. Create a NEW approved owner token restricted to the exact eligible Instagram account; leave immediate publishing unchecked. Assignment operators cannot mint another owner's token. Rotation preserves rights and does not upgrade the original read token.
- For analytics, explicitly approve `zernio.analytics.read` under **Read permissions**. New-token defaults include all read abilities; review and deselect unnecessary grants. Existing tokens do not gain analytics automatically. Create a fresh token with the approved scope; **Rotate** preserves existing rights and does not add this permission.

## API Surface

All paths below are relative to the approved origin. Every route requires a bearer token and the explicit ability shown. Operator-only session routes (`GET /settings/provider-accounts`, `GET /settings/provider-accounts/clients`, `GET /settings/provider-accounts/discover`, `POST /settings/provider-accounts`) are **not** external agent routes, OpenAPI operations or token abilities. Do not expose assignment or global discovery to agents. The contract is eleven operations on ten paths.

| Method | Path                                                       | Required Ability        | Accepted Input                                                                          |
| ------ | ---------------------------------------------------------- | ----------------------- | --------------------------------------------------------------------------------------- |
| GET    | `/api/v1/context`                                          | `context.read`          | None                                                                                    |
| GET    | `/api/v1/capabilities`                                     | `context.read`          | None                                                                                    |
| GET    | `/api/v1/zernio/accounts`                                  | `zernio.accounts.read`  | Query `page`, `limit`                                                                   |
| GET    | `/api/v1/zernio/accounts/{account}/status`                 | `zernio.accounts.read`  | Local account ID                                                                        |
| GET    | `/api/v1/zernio/accounts/{account}/posts`                  | `zernio.posts.read`     | Local account ID; query `page`, `limit`                                                 |
| GET    | `/api/v1/zernio/accounts/{account}/posts/{post}`           | `zernio.posts.read`     | Local account ID; exact post ID                                                         |
| GET    | `/api/v1/zernio/accounts/{account}/posts/{post}/analytics` | `zernio.analytics.read` | Local account ID; 24-lowercase-hex Zernio Post or ExternalPost record ID; no query/body |

Unknown query/body fields are rejected. File uploads are rejected except for the one JPEG on the scheduling route. GET bodies must be empty. ## Responses And Scope

Success is `{"data": ..., "request_id": "<UUID>"}`, with `pagination` for collections. Errors are `{"error":{"code":"...","message":"..."},"request_id":"<UUID>"}`. `request_id` is top-level, not inside `error`. Every response has `X-Request-ID` and `Cache-Control: no-store, private`; 429 also has `Retry-After: 60`. Share only the request ID and sanitized status/code when escalating.

| Status | Error Code                  | Message                      |
| ------ | --------------------------- | ---------------------------- |
| 401    | `unauthenticated`           | `Unauthenticated.`           |
| 402    | `analytics_access_required` | `Analytics access required.` |
| 403    | `forbidden`                 | `Forbidden.`                 |
| 404    | `not_found`                 | `Not found.`                 |
| 409    | `idempotency_conflict`      | `Idempotency conflict.`      |
| 413    | `request_failed`            | `Request failed.`            |
| 422    | `invalid_input`             | `Invalid input.`             |
| 429    | `rate_limited`              | `Rate limited.`              |
| 502    | `provider_unavailable`      | `Provider unavailable.`      |
| 503    | `service_unavailable`       | `Service unavailable.`       |

401 covers invalid/revoked/expired tokens and inactive Clients or invalid ownership. 402 means Zernio analytics access is required, with no upstream billing detail. 403 covers insufficient abilities or disabled publication. Unauthorized selectors are hidden with 404. 409 means conflicting immutable intent or a mapping change. 422 does not expose field-level validation details. Provider-read failures are sanitized as 502. Disabled or unconfigured provider reads return 503, including **account listing**, even though listing itself is local. Publication preflight/provider failures generally become operation states rather than raw provider HTTP errors. Analytics 202 (sync pending) and 424 (all platforms failed) instead retain the `data` envelope; neither means successful metric retrieval.

Account resources expose exactly `id`, `provider`, `environment`, `platform`, `status`, `write_enabled`. They do not expose profile IDs, provider account IDs, credentials, or account names. `mapped` is not proof of live connectivity. Capability discovery is also local; it reflects configuration/mapping/grants, not a provider health check.

Scheduling can contribute `zernio.posts.schedule` and `zernio.write_enabled` only with the explicit token grant, eligible owned Instagram mapping and all gates. The account `write_enabled` uses the corresponding platform/grant eligibility; neither boolean proves live publication. Laravel-rendered oversized-body 413 is sanitized as `request_failed`; a proxy rejection before Laravel may not carry the JSON envelope. An invalid/oversized JPEG normally yields 422. A read-only token receives 403 on scheduling without provider I/O.

`zernio.read_enabled` includes analytics-only grants when the provider is enabled/configured and a current authorized mapping exists. It does not prove a paid analytics entitlement or live connectivity. There is no generic proxy or admin bypass: every target must validate against the current Client, profile and token account scope.

Post resources expose normalized `id`, `profile_id`, `content`, `status`, `scheduled_for`, `created_at`, `updated_at`, `platforms`; each platform target has `account_id`, `platform`, `status`, `url`. These provider IDs are distinct from the safe local account resource. All targets must be currently authorized in the same profile, not merely the requested account. Mixed unauthorized targets are filtered from lists and hidden on detail.

Operation resources expose exactly `id`, `client_id`, `client_account_id`, `capability`, `state`, `provider_post_id`, `created_at`, `updated_at`, `last_reconciled_at`. Intent, result, hashes, leases and private recovery candidates are not public. Operations become invisible if their mapping or current scope no longer matches.

## Pagination And Bounds

- Account and post lists accept `page` 1-1000 (default 1), `limit` 1-100 (default 25).
- Account pagination contains `page`, `limit`, `total`, `pages`, `has_more`, `complete`. `complete` requires page 1 and at most one page.
- Post pagination also contains `scope: provider_page` and `filtered`. Provider totals are not counts of visible authorized posts. `complete` additionally requires no filtering. An empty filtered page is not proof that the account has no posts.
- Operation history accepts **only `limit` and `after`**, never `page` or `total`. Pagination is exactly `limit`, `has_more`, `next_cursor`, `complete`. Follow `next_cursor` as `after` only while `has_more` is true. `complete` is true only without `after` and without more rows. Reads fetch at most `limit + 1` rows and do not count all operations.
- Context, capabilities, account listing and operation reads make zero provider calls. Status makes at most three account-list GETs. Post listing makes one GET.
- Public post detail uses one exact GET; when membership is absent, it uses up to three scoped list GETs of 25: **four total calls and a 75-post fallback horizon**. A safe 404 outside that horizon does not prove universal absence.
- Single-post analytics makes exactly one provider GET pinned to the server-owned profile/account. It accepts no caller query/body overrides and uses the existing read admission budget.
- Immediate publication uses at most three preflight account GETs plus one POST: **four total calls**. Instagram scheduling adds a fixed-host multipart upload POST: **five total calls**, at most 75 network seconds. Reconciliation uses at most one detail GET plus three scoped list GETs per operation attempt: **four GETs**, no upload/publication.
- Each provider call times out after 15 seconds, connects within 5 seconds, disallows redirects, caps response size at 1 MiB, and has no automatic retry. The 75 seconds bound is network time, not a whole-request wall-clock guarantee.
- Database-backed admission applies to both Client and token: defaults 60 reads/minute, 6 writes/minute, maximum two in-flight requests per Client across workers/tokens, stale admission lease 120 seconds. Reconciliation has its own 90-second lease. Poll responsibly and respect `Retry-After`.

Admission/concurrency evidence is from local SQLite tests and source inspection only. Production database row-lock behavior, isolation, multi-worker admission, cache-backed scheduler locks and effective lease timing require separately approved environment checks; this is not a strict production concurrency guarantee.

## Publication And Recovery

The original immediate text-only endpoint remains unchanged: LinkedIn (3000 characters), Facebook (63206), Threads (500), and Bluesky (300). Text must be nonblank valid UTF-8 without forbidden control characters; tabs/newlines/carriage returns are allowed. A JSON request body is simply:

```json
{ "content": "Operator-approved text example" }
```

Send it only with explicit publication approval and a stable `Idempotency-Key` of 1-255 visible ASCII characters without spaces. The key represents one immutable intent across retries and token rotations. Deduplication is durable per Client and capability. Same key plus same intent replays the existing operation; different intent returns 409. Neither an abandoned `pending` operation nor an `unknown` result is resent. Do not change keys to force a retry.

HTTP 200 means a terminal operation (`succeeded`, `failed`, `cancelled`), not necessarily successful publication. HTTP 202 means a nonterminal state (`pending`, `executing`, `provider_pending`, `partial`, `unknown`). Poll the local operation endpoint. Polling neither calls the provider nor reconciles. Provider 207 is ambiguous, not success; a returned candidate ID may be retained privately for read-only recovery and must not be confused with verified public `provider_post_id`.

The walkthrough includes an stdin-only curl publication sample and a separate local operation poll. **Do not execute the publication sample unless separately approved** for the exact public text, Client, account and persisted idempotency UUID. The operator supplies the UUID from the approved intent record; do not generate a new key automatically on retry. Never resend `unknown` by changing the key.

Durable signed webhook receipts and read-only reconciliation support recovery without republishing. Operators, not API clients, manage these commands:

| Command                                                                     | Default Limit                   | Allowed Limit                                | Effect                                                                                                  |
| --------------------------------------------------------------------------- | ------------------------------- | -------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `php artisan agent:process-webhooks --limit=25 --no-interaction`            | 25                              | 1-100                                        | Processes durable receipts; may perform provider reads and update local evidence                        |
| `php artisan agent:reconcile-operations --limit=25 --no-interaction`        | 25                              | 1-100                                        | Reconciles unresolved operations using provider GETs only                                               |
| `php artisan agent:prune-evidence --limit=100 --batches=1 --no-interaction` | 100 per evidence type per batch | 1-1000 rows per type per batch; 1-10 batches | Redacts eligible raw webhook payloads older than 7 days and removes completed audits older than 90 days |

Pruning retains deduplication records; raw payload retention is not deduplication expiry. These commands mutate local evidence and require operator approval.

The standalone prune CLI defaults to `--limit=100 --batches=1`. It permits at most 1000 rows **per evidence type per batch** and 10 batches. A ten-second wall-clock budget is checked **between batches**, not during SQL; it does not interrupt an in-flight query or guarantee a ten-second invocation runtime. It can stop early when both evidence types return fewer than the batch limit. With `--limit=1000 --batches=10`, the upper bound is **10000 rows per evidence type per invocation**, potentially fewer due to eligibility, budget or backlog state. Remaining eligible backlog continues on the next scheduler tick.

The 7-day raw-payload and 90-day completed-audit thresholds define **eligibility, not guaranteed exact expiry**. Actual removal/redaction depends on cron invocation, eligible receipt status and processing leases, backlog size and database/batch budget. Do not claim data is necessarily removed at the instant a retention threshold is reached.

Recovery schedules are **installed in source** in `routes/console.php`:

| Scheduled Command                                | Cadence      | Overlap Protection                               |
| ------------------------------------------------ | ------------ | ------------------------------------------------ |
| `agent:process-webhooks --limit=25`              | Every minute | `withoutOverlapping(60)`, lock expiry 60 minutes |
| `agent:reconcile-operations --limit=25`          | Every minute | `withoutOverlapping(60)`, lock expiry 60 minutes |
| `agent:prune-evidence --limit=1000 --batches=10` | Every minute | `withoutOverlapping(5)`, lock expiry 5 minutes   |

Webhook processing and operation reconciliation share a `when` gate requiring `agent-api.zernio.enabled === true` and `Schema::hasTable` for **each** of `agent_operations`, `clients`, `agent_webhook_receipts`, and `agent_api_audits`. The enabled check precedes those schema checks; each recovery schedule has a 60-minute overlap-lock expiry. **Pruning has a separate schema-only gate** requiring only `agent_webhook_receipts` and `agent_api_audits`, independent of the provider-enabled flag, and a 5-minute overlap-lock expiry. Thus scheduled retention can continue while provider recovery is disabled.

Installed source does not mean deployed or active: host cron/scheduler invocation, effective configuration, schema, cache lock support and any configured asynchronous queue workers remain manual environment checks, not executed here. Do not start workers or enable cron as part of a documentation check. Overlap-lock expiry is not a command-runtime timeout.

Webhook receipt count and operation-candidate count are separate bounds. `ReconcileAgentWebhook` now processes **at most five operation candidates per receipt pass**, fetching at most six candidate IDs to detect another page and persisting the cursor. Local tests cover the five-candidate limit and retention of unresolved earlier pages. Per-operation reconciliation remains at most **four GETs**. A batch/receipt can inspect multiple operations, so four is not a whole-command request ceiling; five candidates can require up to 20 provider GETs per receipt pass. No live queue/worker timing is established by this bound.

## Scheduled Instagram Contract

`POST /api/v1/zernio/accounts/{account}/scheduled-posts` (`agent-api.posts.schedule`) requires `zernio.posts.schedule` with write admission. Multipart has exactly three required fields: nonblank UTF-8 `content` (max 2200 characters, no Unicode controls including newlines), `scheduled_for` (valid UTC `YYYY-MM-DDTHH:mm:ssZ`, no offset/fraction) and uploaded `image` (actual JPEG bytes, at most **2 MiB / 2097152 bytes**, each dimension at most **4096**, at most **16000000 pixels**, width/height ratio **0.5625..1.91** inclusive). No arbitrary URL, base64 source, query/body identity or publication flags are accepted.

A NEW schedule must be **2 minutes through 24 hours** ahead. The server rechecks at least **60 seconds** remain before create and never converts an expired time into immediate publication. Account preflight takes at most three GETs, then fixed-host `POST /v1/media/upload-direct` and `POST /v1/posts`: five calls maximum. Official upload-direct hosting allows 4.5 MB; unattached temporary uploads expire after 7 days, while attaching to a post copies the asset to permanent media storage. Do not apply temporary expiry to the attached post asset. The app deliberately restricts this to a 2 MiB JPEG and next-day scheduling. RWYS does not fetch an untrusted URL source or send its provider secret to a third-party media host.

The `Idempotency-Key` is 1..255 visible ASCII characters with no spaces. Permanent deduplication is per Client/capability/key hash, independent of provider's 24-hour key window. Frozen mapping, exact caption/time, actual file SHA-256, size and MIME are immutable; filename is excluded. Identical authorized replay returns the same operation even after the original deadline without re-upload/create. Changed intent returns 409. Encrypted execution metadata, including the media URL, must be durably stored before create. An ambiguous upload stops at `unknown` and never resends; candidate absence requires operator investigation, not a new key.

Exact caption, validated media identity, UTC instant and a single pending Instagram target under root `scheduled` confirm only `provider_pending` (HTTP 202), **not published**. Terminal replay returns HTTP 200, possibly `failed`/`cancelled`, not necessarily `succeeded`. Only root and target `published` plus a native HTTPS Instagram post URL prove publication during evidence recovery. The new route returns an operation summary only, never the upload/media URL, raw intent, hashes or encrypted execution metadata.

`ZernioApiClient::isSameInstagramMediaUrl` permits exact URL equality or only the strict HTTPS `media.zernio.com` promotion from `/temp/` to `/media/` with the same ASCII basename (`[A-Za-z0-9_-]{1,251}.jpg`). The promotion exception accepts no query, fragment, credentials, port, encoding or traversal; all other URL pairs require exact equality. It neither mutates the upload source/frozen intent nor performs a byte fetch itself. The independent matching-hash CDN check in the live record corroborated identity for this one image; the exception is not a license to trust arbitrary moved URLs or skip media-identity verification. Official permanent-copy behavior is documented at https://docs.zernio.com/guides/media-uploads.mdx.

JPEG validation checks actual byte size, MIME, image headers/dimensions and SOI/EOI markers; it is **not full bitmap decoding**. GD/Imagick are absent and no dependency was added. The live Canvas image was valid, but a malformed JPEG satisfying local structural checks may still be rejected by the provider. No full local decode guarantee is claimed.

General post/scoped-list normalization can validate media for internal reconciliation; media URLs remain private, not added to public post/operation responses. Evidence GETs may continue after write flags and account publishing permission are revoked, provided provider reads/configuration, active Client, owned profile and unchanged active mapping still authorize evidence. No candidate or inconclusive evidence means unresolved/operator investigation, never automatic resend. Public operation polling is local and does not reconcile.

Enable an approved eligible owned production Instagram mapping only through trusted server CLI `php artisan agent:account-publishing <LOCAL_ACCOUNT_ID> --no-interaction`, after all server gates, active Client/profile claim and verified owner checks. `--disable` can disable any existing mapping; it does not require re-enabling invalid eligibility. This CLI is a separate approved database write, not a token mint or HTTP admin bypass. It also retains existing four-platform text support.
